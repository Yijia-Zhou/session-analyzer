## Accepted history / 已接受历史

### M0 attribution / M0 归因

M0 established that the strict Codex cold build performs a complete first relationship parse and a complete final parse for every ordinary candidate, with independent accepted-prefix verification in each parse. On its sealed snapshot, the relationship pass constructed 379,690 Raw rows and 289,941 Logical rows, reached about 1.072 GB peak heap, retained about 303.7 MB after relationship projection, and had a roughly 57.842-second median. These are historical attribution facts, not M2 speedup promises or current gates. / M0 确立：严格 Codex 冷构建会对每个普通 candidate 执行完整的首次关系 parse 与完整 final parse，并在每次 parse 中独立验证 accepted prefix。在其封存 snapshot 上，关系 pass 构造了 379,690 条 Raw 与 289,941 条 Logical，heap 峰值约 1.072 GB，关系投影后保留约 303.7 MB，median 约 57.842 秒。这些只是历史归因，不是 M2 加速承诺或当前 gate。

M1 defined one transient `CodexRelationshipEvidenceV1` contract consumed by existing materialized-fork, review-parent, Earlier Branch, cycle, and final-parse logic. A later sealed characterization separated ordinary and deep-evidence candidates, but its candidate counts and timings remain descriptive only. M2 must produce the existing evidence shape directly for LIGHT candidates and must not create a second long-lived relationship model. / M1 定义了由既有 materialized-fork、review-parent、Earlier Branch、cycle 与 final-parse 逻辑消费的单一瞬态 `CodexRelationshipEvidenceV1` contract。之后的封存 characterization 区分了 ordinary 与 deep-evidence candidate，但其 candidate count 与 timing 只作描述。M2 必须为 LIGHT candidate 直接产生既有 evidence shape，不得创建第二套长期关系模型。

## M2 implementation boundary / M2 实现边界

```text
candidate inspection
→ initial global deep-evidence planning
→ relationship pass
   LIGHT: Codex-local streaming relationship evidence scan
   FULL_FIRST_PARSE: existing parseSessionFile()
                     + buildCodexRelationshipEvidence()
→ accepted-prefix deep-plan revalidation and one-way promotion
→ unchanged relationship inference
→ unchanged cycle prerequisite parses
→ unchanged final accepted-prefix parses
→ unchanged query/index construction
```

The LIGHT scanner fixes source size and identity at start, reads exactly the accepted prefix, hashes the delivered bytes, processes JSONL one line at a time, retains only bounded relationship facts, independently re-hashes the same prefix with `hashFilePrefix()`, and verifies byte count, digest, size, and file identity. Append-only suffix growth is ignored; rewrite, shrink, removal, identity replacement, short reads, and digest mismatch preserve existing failure behavior. / LIGHT scanner 在开始时固定 source size 与 identity，只读取 accepted prefix，对 delivered byte 流式 hash，逐行处理 JSONL，只保留有界关系 fact，随后用 `hashFilePrefix()` 独立重哈希同一 prefix，并验证 byte count、digest、size 与 file identity。Append-only suffix growth被忽略；rewrite、shrink、removal、identity replacement、short read 与 digest mismatch 保持既有失败行为。

LIGHT evidence preserves the exact current distinctions among physical lines, blank lines, nonblank malformed or falsy JSON, and truthy JSON records. It extracts identity, source metadata, CWD association, ancestry, timestamps, counts, first-two-Raw identity facts, sparse review lifecycle facts, and aggregate timestamp validity without building complete Raw/Logical graphs, analysis, presentation indexes, image descriptors, search/preview text, Raw compaction arrays, canonical digest arrays, or Logical ownership ranges. `_canonicalRawDigests` and `_forkLogicalRanges` remain `[]`. / LIGHT evidence 精确保留当前 physical line、blank line、非空 malformed／falsy JSON 与 truthy JSON record 的区别。它提取 identity、source metadata、CWD association、ancestry、timestamp、count、前两条 Raw identity fact、稀疏 review lifecycle fact 与聚合 timestamp validity；不构造完整 Raw／Logical graph、analysis、presentation index、image descriptor、search／preview text、Raw compaction array、canonical digest array 或 Logical ownership range。`_canonicalRawDigests` 与 `_forkLogicalRanges` 保持为 `[]`。

Candidate inspection, LIGHT scanning, and full relationship parsing share the same leading-session planning semantics. Accepted-prefix projections are recomputed globally before inference. Effective deep paths are the union of initial inspection planning and accepted-prefix planning; newly deep paths are promoted through the existing full parser with canonical Raw digests, and no FULL candidate is downgraded during the build. / Candidate inspection、LIGHT scanning 与完整关系 parsing 共享相同的 leading-session planning semantic。在 inference 前会全局重新计算 accepted-prefix projection。有效 deep path 是初始 inspection planning 与 accepted-prefix planning 的并集；新出现的 deep path 通过既有完整 parser 携带 canonical Raw digest 单向提升，同一 build 中不会把 FULL candidate 降级。

Malformed or otherwise uncertain LIGHT input fails closed to the existing full relationship parse. Initial deep candidates normally receive only that full parse, without an extra full-file LIGHT scan. The production output and progress model expose no LIGHT/FULL state; a test-only observation hook proves classification. / Malformed 或其他不确定的 LIGHT input 会 fail closed 到既有完整关系 parse。初始 deep candidate 通常只执行该完整 parse，不增加一次全文件 LIGHT scan。Production output 与 progress model 不暴露 LIGHT／FULL 状态；分类仅由 test-only observation hook 证明。
