# v0.1.3 freeze and release / v0.1.3 冻结与发布

## Objective / 目标

Freeze the already implemented Claude Code source-adapter increment as `session-analyzer@0.1.3`, merge it to `main` only through the normal pull-request path, and release the exact verified main commit through the repository's staged OIDC workflow. Complete staged-artifact review, phishing-resistant maintainer approval, anonymous Windows/Linux public verification, and only then create `v0.1.3` and the GitHub Release. / 将已经实现的 Claude Code 来源适配器增量冻结为 `session-analyzer@0.1.3`，只通过正常 pull request 路径合入 `main`，并通过仓库的 staged OIDC workflow 发布精确验证过的 main commit。完成 staged artifact 审查、抗钓鱼的维护者审批、匿名 Windows/Linux 公共验证后，才创建 `v0.1.3` 与 GitHub Release。

This plan is the durable public version-specific release record. It references `docs/design-docs/npm-release-runbook.md` as the authoritative procedure and does not redefine or weaken that runbook. Raw command output, account-side readback, machine-specific details, and transient diagnostics belong only in the Git-ignored maintainer-local appendix. / 本计划是长期公开的版本专属发布记录。权威流程以 `docs/design-docs/npm-release-runbook.md` 为准；本计划不重新定义或削弱该运行手册。原始命令输出、账户侧 readback、本机特有信息与临时诊断只进入 Git 忽略的维护者本地附录。

## Frozen release decisions / 已冻结的发布决策

1. `0.1.3` is a feature freeze. No further user-facing feature is added during release preparation; only release metadata, documentation convergence, package-contract hardening, validation fixes, and evidence recording are in scope. / `0.1.3` 已进入功能冻结。发布准备期间不再增加面向用户的功能；范围只包括发布 metadata、文档收敛、package contract 加固、验证修复与证据记录。
2. The source branch is reviewed through a normal pull request. Do not modify or merge local `main` directly. / 来源分支通过正常 pull request 接受审查。不得直接修改或合并本地 `main`。
3. The exact release source is determined only after the release pull request is merged, the resulting `main` commit is pushed, required CI is green, and a clean checkout identifies that exact SHA. / 只有发布 pull request 合入、生成的 `main` commit 已 push、必要 CI 全绿且干净 checkout 确认精确 SHA 后，才能确定 release source。
4. All evidence collected on `bce52a6` before metadata freeze is preliminary. Every source, metadata, test, generated-asset, or documentation change invalidates candidate and dry-run evidence and requires fresh validation. / Metadata 冻结前在 `bce52a6` 上收集的全部证据都是 preliminary evidence。任何源码、metadata、测试、生成资产或文档变更都会使候选与 dry-run 证据失效，并要求重新验证。
5. The staged OIDC path is mandatory unless this plan records a concrete staged-publishing outage and the maintainer explicitly authorizes the runbook's manual fallback. No local tarball may be published directly. / 除非本计划记录具体的 staged-publishing 故障且维护者明确授权运行手册中的手动 fallback，否则必须使用 staged OIDC 路径。不得直接发布本地 tarball。
6. `publish.yml` is manually dispatched from `main` with exact input `0.1.3` only after a fresh public-registry check and explicit maintainer authorization. The staged artifact uses immutable intended tag `latest`. / 只有在重新检查公共 registry 并得到维护者明确授权后，才能从 `main` 手动 dispatch `publish.yml`，且输入必须精确为 `0.1.3`。Staged artifact 使用不可变的预期 tag `latest`。
7. The staged package is reviewed for identity, manifest, provenance, workflow source SHA, and downloaded tarball SHA-256 before approval. Approval uses a registered WebAuthn authenticator or hardware security key; TOTP is not a release-approval fallback. / Approve 前必须检查 staged package 的身份、manifest、provenance、workflow 来源 SHA 与下载 tarball SHA-256。审批使用已注册的 WebAuthn authenticator 或硬件安全密钥；TOTP 不作为发布审批 fallback。
8. Anonymous Windows and Linux exact-version verification must pass after approval. Only afterward may the exact release commit receive annotated tag `v0.1.3` and a bilingual GitHub Release. / Approve 后必须通过匿名 Windows 与 Linux 精确版本验证。随后才可以为精确 release commit 创建 annotated tag `v0.1.3` 与双语 GitHub Release。
9. Both this plan and the Trusted Publishing acceptance plan remain active until public verification, tag, GitHub Release, and final evidence are complete. / 在公共验证、tag、GitHub Release 与最终证据全部完成前，本计划与 Trusted Publishing acceptance 计划都保持 active。

## Version-specific risks / 版本特有风险

### Claude Code adapter first release / Claude Code 适配器首发

`0.1.3` is the first public package to expose the explicit `--source claude-code` path, source-native Claude interpretation, namespaced identities, indexed Raw Record reads, nested subagent containment, and pointer-fork context. In addition to focused and browser coverage, the installed package smoke must exercise a synthetic Claude home through the packaged CLI/server rather than proving only that the files appear in a manifest. / `0.1.3` 是首次公开提供显式 `--source claude-code` 路径、来源原生 Claude 解释、带命名空间 identity、索引 Raw Record 读取、嵌套 subagent containment 与 pointer-fork 上下文的 package。除聚焦测试与 browser coverage 外，安装后 package smoke 必须通过打包后的 CLI/server 运行合成 Claude home，而不能只证明文件出现在 manifest 中。

### First live Trusted Publishing acceptance / Trusted Publishing 首次真实验收

The external binding has been reviewed but has not yet completed a real staged submission. A public `npm view` `E404` proves only that `0.1.3` is not public; it cannot distinguish an absent version from a private staged version. Any ambiguous workflow or npm result blocks retry until the workflow log and staged-package view are reviewed according to the runbook. / 外部 binding 已完成审查，但尚未通过真实 staged submission。公共 `npm view` 的 `E404` 只能证明 `0.1.3` 尚未公开，不能区分版本不存在与已私有 staging。Workflow 或 npm 结果含糊时，必须按运行手册检查 workflow log 与 staged-package 页面，在此之前不得重试。

### Release environment registry / 发布环境 registry

Release work must use a temporary release shell or isolated configuration whose effective registry is exactly `https://registry.npmjs.org/`; do not rely on or persistently rewrite any ordinary user-level npm configuration. / 发布工作必须使用临时 release shell 或隔离配置，并确保有效 registry 精确为 `https://registry.npmjs.org/`；不得依赖或持久改写任何日常用户级 npm 配置。

- Commit and push only with explicit authorization, open a normal pull request, and require the repository's Linux/Windows CI before merge. / 只有得到明确授权后才 commit 与 push，建立正常 pull request，并在合入前要求仓库 Linux/Windows CI。

### Phase 3: Establish the exact release commit on main / 在 main 上确定精确 release commit

- After the pull request merges, identify the pushed main SHA and its CI run URL. / Pull request 合入后，确认已 push 的 main SHA 及其 CI run URL。

### Phase 4: Stage and approve through OIDC / 通过 OIDC staging 并 approve

- Recheck official public registry versions and dist-tags immediately before dispatch. / Dispatch 前立即重新检查官方公共 registry 的 version 与 dist-tag。
- With explicit maintainer authorization, dispatch **Stage npm release** from `main` with exact input `0.1.3`. / 得到维护者明确授权后，从 `main` dispatch **Stage npm release**，输入精确 `0.1.3`。
- Confirm verify-job gates, source SHA, candidate SHA-256, stage-job byte reproduction, and the single OIDC staging mutation. / 确认 verify-job gate、来源 SHA、候选 SHA-256、stage-job 字节复现与唯一一次 OIDC staging mutation。
- Inspect the staged identity, `latest` intent, manifest, provenance, workflow source, and downloaded SHA-256. Reject and investigate any mismatch. / 检查 staged identity、`latest` 意图、manifest、provenance、workflow 来源与下载 SHA-256。出现任何不一致时 reject 并调查。
- Approve only through maintainer-controlled WebAuthn or a hardware security key. / 只能通过维护者控制的 WebAuthn 或硬件安全密钥 approve。

### Phase 5: Verify publicly, tag, and release / 公共验证、tag 与 release

- Perform demonstrably anonymous exact-version verification on clean Windows and Linux, including npx, global install, CLI help, packaged server root, and `/api/state`. / 在干净 Windows 与 Linux 上执行可证明匿名的精确版本验证，包括 npx、全局安装、CLI help、packaged server root 与 `/api/state`。

- Only after public verification, create and push annotated `v0.1.3` at the exact release commit and publish the bilingual GitHub Release. / 只有公共验证通过后，才在精确 release commit 上创建并 push annotated `v0.1.3`，随后发布双语 GitHub Release。
