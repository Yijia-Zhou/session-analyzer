## Context / 背景

Codex transcript JSONL files contain multiple channels for the same semantic action. A user message can appear as both `response_item.message role=user` and `event_msg.user_message`. Assistant responses, reasoning, tool calls, and proposed plans may also be mirrored or split across multiple rows. Transcript formats also evolve over time, so old sessions and new sessions cannot be normalized with a single simplistic rule.

Codex 转录 JSONL 文件会为同一个语义动作包含多个通道。用户消息既可能以 `response_item.message role=user` 出现，也可能以 `event_msg.user_message` 出现。助手回复、推理、工具调用和计划产物也可能被镜像或拆分到多行中。转录格式还会随时间演进，因此旧会话和新会话无法用一个简单规则归一化。

The first version of this repository rendered raw records directly, which caused duplicate messages and exposed protocol injections in the main reading flow.

本仓库的第一个版本直接渲染原始记录，这导致消息重复，并在主阅读流程中暴露协议注入。

## Design goals / 设计目标

- Derive a stable, readable logical timeline from noisy raw transcript rows. / 从嘈杂的原始转录行中派生稳定、可读的逻辑时间线。
- Preserve traceability back to original JSONL lines. / 保留回溯到原始 JSONL 行的可追踪性。
- Support both newer and older Codex transcript formats. / 同时支持较新和较旧的 Codex 转录格式。
- Keep the main timeline readable without hiding important debugging information forever. / 保持主时间线可读，同时不永久隐藏重要调试信息。

## Non-goals / 非目标

- Lossless semantic reconstruction of every historical transcript quirk / 对每个历史转录怪异情况进行无损语义重建
- Cloud-scale indexing or storage optimization / 云规模索引或存储优化
- Rewriting transcript files into a canonical on-disk format / 将转录文件重写为规范的磁盘格式

## Proposed design / 提议设计

### High-level architecture / 高层架构

1. Parse JSONL into `rawEvents`. / 将 JSONL 解析为 `rawEvents`。
2. Build `logicalEvents` on top of `rawEvents`. / 在 `rawEvents` 之上构建 `logicalEvents`。
3. Serve one of three layers: / 提供三层之一：
   - `main` / 主时间线层
   - `protocol` / 协议层
   - `raw` / 原始记录层

### Main components / 主要组件

- Codex source/raw parser in `src/codex-source.js`, assembled by `src/codex.js` / `src/codex-source.js` 中的 Codex source/raw 解析器，并由 `src/codex.js` 组装
- Codex logical-event builder in `src/codex-logical.js`, assembled by `src/codex.js` / `src/codex-logical.js` 中的 Codex 逻辑事件构建器，并由 `src/codex.js` 组装
- HTTP API in `server.js` / `server.js` 中的 HTTP API
- Layer-aware UI rendering in `public/app.js` / `public/app.js` 中的层感知 UI 渲染

### Data flow / 数据流

1. Load session metadata and raw JSONL rows. / 加载会话元数据和原始 JSONL 行。
2. Before full parsing, pre-scan transcript `cwd` metadata to select candidate files for the target repository. Files whose `cwd` matches the target repository enter the candidate set, files known to belong only to other repositories are skipped, and files with no `cwd` metadata are counted as unknown without full parsing or display. / 在完整解析前，先预扫描转录中的 `cwd` metadata，为目标仓库选择候选文件。`cwd` 匹配目标仓库的文件会进入候选集合，已知只属于其他仓库的文件会被跳过，而没有 `cwd` metadata 的文件会计入 unknown，不会再做完整解析，也不会显示。
3. Annotate each raw row with extracted text, call IDs, command text, outputs, and touched files when available. / 在可用时，为每个原始行标注提取文本、调用 ID、命令文本、输出和触及文件。
4. Group by `call_id` first for tool operations. / 对工具操作先按 `call_id` 分组。
5. Walk the remaining rows in order and fold them into logical messages, reasoning entries, protocol events, lifecycle events, or proposed plans. / 按顺序遍历剩余行，并折叠为逻辑消息、推理条目、协议事件、生命周期事件或 proposed plan。
6. Expose logical events to the main and protocol layers; expose raw rows separately. / 向主层和协议层暴露逻辑事件；单独暴露原始行。

Reasoning text extraction is intentionally narrower than generic raw-field text flattening. A `response_item.reasoning` row uses `summary_text` entries first, then falls back to `reasoning_text` content entries when the summary is empty. An `event_msg.agent_reasoning` row accepts only string `message` or `text` fields. Retained reasoning text, including detail text assembled from mirrored rows, is capped at 16,000 characters; unknown content types or shapes and `encrypted_content` are not promoted into Main timeline text or the readable-reasoning folding condition.

Reasoning 文本提取有意比通用原始字段文本扁平化更严格。`response_item.reasoning` 行会优先使用 `summary_text` 条目，当 summary 为空时再回退到 `reasoning_text` content 条目。`event_msg.agent_reasoning` 行只接受字符串类型的 `message` 或 `text` 字段。保留的 reasoning 文本（包括从镜像行组合出的详情文本）会限制在 16,000 个字符以内；未知 content 类型或形态和 `encrypted_content` 不会被提升为 Main timeline 文本，也不会命中可读 reasoning 折叠条件。

Web search records are normalized as adjacent mirrored rows rather than normal `call_id` tool groups. Real transcripts may write `event_msg.web_search_end` before the completed `response_item.web_search_call` snapshot, often with matching action metadata and identical or near-identical timestamps. The logical builder merges adjacent search/open-page rows by canonical action target so the main timeline shows one web search event with both raw refs. When action metadata is absent or incomplete, timestamp fallback pairing is limited to rows from the same `turn_id`; call-only and end-only historical rows remain visible as single logical events.

Web 搜索记录会按相邻镜像行归一化，而不是按普通 `call_id` 工具分组处理。真实转录可能先写入 `event_msg.web_search_end`，再写入已完成的 `response_item.web_search_call` 快照，二者通常带有匹配的 action 元数据，并且时间戳相同或非常接近。逻辑构建器会按规范化后的 action 目标合并相邻的搜索/打开页面记录，使主时间线只显示一个带有两个原始引用的 Web 搜索事件。当 action 元数据缺失或不完整时，基于 timestamp 的兜底配对只会作用于同一个 `turn_id` 内的行；只有 call 或只有 end 的历史行仍保留为单独逻辑事件。

Hook lifecycle records are normalized only when the JSONL row itself is explicit: `event_msg` rows with `hook_begin` / `hook_end` / `hook_declined` or newer `hook_started` / `hook_completed` payload types become Main timeline `kind: hook` events. Rows with the same `call_id` are grouped; rows without a `call_id` remain single hook events. The label prefers hook-name fields in the payload, then `tool_name`, then `Hook`; status comes from the terminal row as `completed`, `declined`, `failed`, or `incomplete`.

Hook 生命周期记录只在 JSONL 行本身明确时才会归一化：payload type 为 `hook_begin` / `hook_end` / `hook_declined` 或新版 `hook_started` / `hook_completed` 的 `event_msg` 行会变成 Main timeline 的 `kind: hook` 事件。带有同一 `call_id` 的行会合并；没有 `call_id` 的行会保留为单行 hook 事件。label 优先使用 payload 中的 hook 名称字段，其次使用 `tool_name`，最后回退为 `Hook`；status 来自终态行，取 `completed`、`declined`、`failed` 或 `incomplete`。

Unwrapped `response_item.message` rows with `role=developer` are not assumed to be hooks. If the text is a known protocol wrapper such as permissions, collaboration mode, environment context, goal context, skill injection, or another XML-like metadata block, it remains in the protocol layer. Otherwise it becomes a protocol-layer `kind: developer_message` event tagged `Possible hook output`. This preserves startup output seen by the TUI without claiming a precise hook source when the JSONL row lacks one, while keeping runtime/hook stdout out of the Main timeline. Current samples can show an outer TUI title such as `SessionStart hook`, but that title is not present in the raw JSONL row and cannot be reconstructed exactly from the row alone.

未包装的 `response_item.message role=developer` 行不会被直接假定为 hook。如果文本是已知协议包装，例如 permissions、collaboration mode、environment context、goal context、skill injection 或其他 XML-like metadata block，它仍保留在 protocol 层。否则它会变成 protocol 层的 `kind: developer_message` 事件，并带有 `Possible hook output` tag。这样可以保留 TUI 中可见的 startup 输出，同时在 JSONL 行缺少明确来源时不声称精确 hook 来源，并把运行时/hook stdout 排除在主时间线之外。当前样本可能在 TUI 中显示 `SessionStart hook` 这样的外层标题，但该标题没有进入原始 JSONL 行，不能仅凭该行精确还原。

User-initiated `<user_shell_command>` wrappers from `response_item.message` role `user` or `event_msg.user_message` are promoted to Main timeline events with `kind` and `subtype` both set to `user_shell_command`. They have a dedicated user shell command label/title for display, preserve raw refs, and expose the command/result wrapper in preview and detail, but they are not normal `user_message` events.

来自 `response_item.message` role `user` 或 `event_msg.user_message` 的用户发起 `<user_shell_command>` 包装会被提升为 Main timeline 事件，`kind` 和 `subtype` 都设为 `user_shell_command`。它们有专用的用户 shell command 展示 label/title，保留 raw refs，并在 preview 和 detail 中暴露 command/result 包装内容，但它们不是普通的 `user_message` 事件。

Session identity is fixed from the transcript file UUID or the first `session_meta` row. Later embedded `session_meta` rows, such as parent metadata copied into a forked subagent transcript, remain inspectable protocol/raw records but do not replace the owning session id or selection key.

会话身份固定来自转录文件 UUID 或第一条 `session_meta` 行。后续嵌入的 `session_meta` 行，例如 fork 出来的子 agent 转录中复制进来的父会话元数据，仍然作为可检查的协议/原始记录保留，但不会替换所属会话 id 或选择 key。

Session title inference prefers explicit `session_index.jsonl` or owned thread-name metadata. When no explicit title exists, fallback inference scans only main-layer `user_message` events, so `user_shell_command` events do not affect fallback titles; it then cleans lightweight Markdown title syntax and uses the first valid task line. Forked subagent sessions and unproven plain `/fork` sessions retain the last-valid-task fallback. A proven Materialized Fork Session excludes inherited context first and therefore uses the first valid user task from its own continuation.

会话标题推断优先使用显式的 `session_index.jsonl` 或当前会话拥有的 thread-name 元数据。当不存在显式标题时，回退推断只扫描主层 `user_message` 事件，因此 `user_shell_command` 事件不会影响回退标题；随后清理轻量 Markdown 标题语法，并使用第一条有效任务行。fork 出来的子 agent 与证据未成立的普通 `/fork` 会话保留“最后一条有效任务”的回退。证据成立的物化式分叉会话会先排除继承上下文，因此使用自身续写中的第一条有效用户任务。

Session summaries expose derived-session display metadata for subagent and review children. Only explicit subagent metadata such as `source.subagent.thread_spawn.parent_thread_id` or `thread_source: "subagent"` marks a session as derived; a plain `forked_from_id` alone records normal `/fork` ancestry but does not make the session visually secondary. Review-like metadata is classified as `review`; other derived children remain `subagent`. A top-level `parent_thread_id` is explicit parent evidence only when independent metadata has already classified the session as a derived `review` or `subagent`; explicit linkage wins and keeps `parentSessionInferred` false, while an otherwise-primary session with that field alone remains unlinked. Review transcripts without an explicit parent id fall back to temporal inference only when exactly one normal same-repo session records matching review lifecycle events around the review child. Both the legacy dedicated `entered_review_mode` / `exited_review_mode` rows and the canonical completed TurnItem envelope (`event_msg` `item_completed` with `item.type` `EnteredReviewMode` / `ExitedReviewMode`) normalize to the same review lifecycle; rows carrying a `thread_id` are accepted only for the owning session. When the parent or fork source session is indexed, summaries include its title so the frontend can label the relationship. In the ordinary session list, the frontend builds a cycle-safe hierarchy from derived `parentSessionId` relationships, keeps backend sort order among roots and siblings, and collapses child groups by default. A compact child-count disclosure bridges the center of each parent card's bottom border so the selectable card keeps its full width while expansion remains a separate action; selecting or drilling down to a child expands its ancestor groups. Missing-parent and cycle-rejected derived sessions remain visible as roots, and project-search results remain flat so an independently matching child is never hidden. Normal fork sessions remain primary rows with a fork-source tag. This hierarchy changes presentation only, not selection identity, filtering, project-search membership, or timeline construction.

会话摘要会为 subagent 和 review 子会话暴露派生会话展示元数据。只有 `source.subagent.thread_spawn.parent_thread_id` 或 `thread_source: "subagent"` 等显式 subagent 元数据会把会话标记为派生会话；单独的 `forked_from_id` 只记录普通 `/fork` 祖先关系，不会让会话在视觉上变成次级。metadata 呈现 review 语义的子会话分类为 `review`；其他派生子会话保持为 `subagent`。只有独立 metadata 已把会话判定为派生的 `review` 或 `subagent` 时，顶层 `parent_thread_id` 才会作为显式父会话证据被接受；显式关联优先，并保持 `parentSessionInferred` 为 false，而其他仍属 primary 的会话即使仅有该字段也不会建立关联。缺少显式父会话 id 的 review 转录，只在恰好一个同仓库普通会话记录了与 review 子会话匹配的 review 生命周期事件时回退到时间推断。旧的专用 `entered_review_mode` / `exited_review_mode` 记录与 canonical 的 completed TurnItem envelope（`event_msg` 的 `item_completed`，`item.type` 为 `EnteredReviewMode` / `ExitedReviewMode`）会归一化为同一 review 生命周期；携带 `thread_id` 的记录只接受属于当前会话的那一份。当父会话或 fork 来源会话已被索引时，摘要会包含其标题，使前端能标记关系。在普通 Session 列表中，前端根据派生会话的 `parentSessionId` 构建防循环层级，在根节点和同级子节点内保持后端排序，并默认折叠子会话组。紧凑的子会话数量 disclosure 桥接在父卡片底边中央，使可选择的卡片保持完整宽度，同时让展开仍是独立操作；选择子会话或从项目搜索下钻到子会话时会展开其祖先组。缺少父会话或因循环关系被拒绝归组的派生会话仍作为根节点可见；项目搜索结果保持平铺，避免独立命中的子会话被隐藏。普通 fork 会话仍保持主会话行并显示 fork 来源标签。该层级只改变展示，不改变选择身份、筛选、项目搜索成员关系或时间线构建。

Codex fork inference preserves two Logical projections. The complete private projection continues to reference every physical Raw Record and is reusable across reindex. The public projection removes only events wholly inside a proven materialized inherited range; a Logical Event whose references are missing or span fork metadata, inherited context, and continuation prevents ownership inference entirely. Counts, analysis, presentation indexes, event catalogs, Logical totals, Main/Protocol search, and file suggestions are rebuilt from the public projection after inference. Raw remains the physical file and exposes `forkSegment` plus `inheritedFromSessionId` for inherited rows. / Codex fork inference 会保留两份逻辑投影。完整的内部投影继续引用每条物理 Raw Record，并可在 reindex 时复用。公开投影只移除完整落在已证实物化继承范围内的事件；若某个逻辑事件的引用缺失，或跨越分叉元数据、继承上下文与续写区段，则整个 ownership 推断都会失败。计数、分析、presentation index、事件目录、逻辑总计、Main／Protocol 搜索和文件建议都在推断后从公开投影重建。Raw 继续表示物理文件，并为继承行暴露 `forkSegment` 与 `inheritedFromSessionId`。

An Earlier Branch edge reverses the ordinary source-to-fork display direction without changing identity: the inactive source row is nested beneath its sole continuing Materialized Fork Session. The edge requires a non-Derived child with owned Main activity, one ordinary fork child in the retained index, valid timestamps, no source Raw Record strictly later than `forkedAt`, and a cycle-safe relationship. Chains may fold repeatedly. Multiple ordinary children, later source activity, invalid timestamps, missing successors after filtering, or cycles remain roots. Derived and Earlier edges share the cycle-safe hierarchy; a mixed group is labeled `Related sessions`, while project-search cards stay flat. / 较早分支 edge 会反转普通“来源到 fork”的展示方向，但不改变 identity：不再活跃的来源行嵌套在其唯一续写的物化式分叉会话下。该 edge 要求 child 非派生且已有自有 Main 活动、当前保留索引中只有一个普通 fork child、时间戳有效、来源 Raw 中没有严格晚于 `forkedAt` 的记录，并且关系防循环。链可逐级折叠。多个普通 child、来源后续活动、无效时间戳、筛选后 successor 缺失或循环都会保持为根行。派生 edge 与较早分支 edge 共用防循环层级；混合组标记为“相关会话”，项目搜索卡片继续平铺。

Both the legacy dedicated `entered_review_mode` / `exited_review_mode` raw records and the canonical completed TurnItem rows produce Main timeline lifecycle events with kind `review`, so the parent session's readable timeline retains the point where review was requested and the point where review output returned.

旧的专用 `entered_review_mode` / `exited_review_mode` 原始记录和 canonical 的 completed TurnItem 记录都会生成 Main timeline 中 kind 为 `review` 的生命周期事件，使父会话的可读时间线保留发起 review 和收到 review 输出的位置。

## Data model / schema / 数据模型 / 模式

Canonical DTOs use a small source envelope so raw, logical, and detail payloads can be interpreted without assuming Codex JSONL implementation details. `schemaVersion` is the Session Analyzer canonical DTO version, starts at `1`, and is independent from any upstream protocol version. `sourceKind` is a stable machine identifier for the source system; v0.1 emits only `codex`, while future adapters may add other values without localizing this field. `sourceSchemaVersion` is optional and should be populated only when the source provides a trustworthy schema or protocol version.

规范 DTO 使用一个小型 source envelope，使 raw、logical 和 detail payload 可以被解释，而不需要假设 Codex JSONL 实现细节。`schemaVersion` 是 Session Analyzer 自己的规范 DTO 版本，初始为 `1`，与任何上游协议版本相互独立。`sourceKind` 是来源系统的稳定机器标识；v0.1 只输出 `codex`，未来 adapter 可以增加其他值，但该字段不得本地化。`sourceSchemaVersion` 是可选字段，只应在来源提供可信 schema 或协议版本时填充。

Source locations use typed locators instead of assuming every source can be addressed by file and line. Current Codex rows use `sourceLocator: { type: "jsonl_line", file, line }`; the `file` value is a project-generated JSONL locator path normalized to forward slashes for cross-platform DTO stability. Future sources may use different locator types such as database rows or stream offsets. During compatibility migration, existing Codex `source`, `rawRefs[].file`, `rawRefs[].line`, and `rawRefs[].rawId` fields remain available and preserve their original parser path strings, but new code should use `sourceLocator` when it needs source identity and must not assume every locator has file and line properties.

来源位置使用 typed locator，而不是假设每种来源都能用文件和行号寻址。当前 Codex 行使用 `sourceLocator: { type: "jsonl_line", file, line }`；其中 `file` 是项目生成的 JSONL locator path，并归一化为前斜杠，以保持跨平台 DTO 稳定。未来来源可以使用其他 locator 类型，例如数据库行或流 offset。在兼容迁移期间，现有 Codex `source`、`rawRefs[].file`、`rawRefs[].line` 和 `rawRefs[].rawId` 字段继续可用，并保留原始 parser path 字符串；但新代码在需要来源身份时应使用 `sourceLocator`，并且不得假设每个 locator 都有 file 和 line 属性。

Repository roots, transcript `cwd` values, and absolute touched-file paths select Windows or POSIX path semantics from the path string itself rather than from the analyzer host OS. Windows drive and UNC paths use `path.win32`, including case-insensitive containment; leading-slash paths use `path.posix` with case-sensitive containment. Relative paths continue to use host semantics. This keeps copied or sanitized transcript replay stable across Linux and Windows without changing legacy raw-ref path strings.

Repository root、transcript `cwd` 值与绝对 touched-file path 会根据路径字符串自身选择 Windows 或 POSIX path 语义，而不是沿用 analyzer 宿主操作系统。Windows drive 与 UNC path 使用 `path.win32`，包含不区分大小写的 containment；以斜杠开头的 path 使用 `path.posix`，containment 区分大小写。相对路径继续使用宿主语义。这样可在不改变 legacy raw-ref path 字符串的前提下，使复制或脱敏 transcript 的 replay 在 Linux 与 Windows 间保持稳定。

`sourceRecordType` and `sourceEventType` use refs-only semantics. Raw DTOs may expose the precise source row types at the top level. Logical and detail DTOs do not expose potentially misleading aggregate `sourceRecordType` or `sourceEventType` fields; each `rawRefs[]` entry carries the precise row-level types instead, and `rawRefs[]` remains the authoritative traceability surface for multi-row logical events.

浏览器拥有显式的 `searchScope`、`searchQuery` 和 `searchFilters = { file, kind, status, codeModeRequest }` 状态；输入框元素只是可编辑自由文本投影，绝不解析操作符。`layerId` 仍是唯一的应用事件层状态。单行 HUD 投影范围、筛选数、紧凑范围计数和 session 导航；唯一的全局层级选择器紧邻搜索框保留，不在 HUD 中重复。其非模态搜索选项表面在同一状态上提供两种展示模式：HUD 的范围和筛选胶囊打开参数模式并把焦点移到对应控件；输入框在已有 query 时获得焦点或继续输入，只打开紧凑结果模式。参数模式只对依赖结果的信息采用渐进披露，固定的快速筛选控件始终可见：类型与状态同处一行，稳定的 `file` key 显示为“涉及文件”并独占下一行，每个空的“任意……”值都会直接清除对应筛选。在 Main 层，类型使用一个原生分组选择器：`Code Mode 工具调用` 分组不含“全部 operation”选项，只包含“脚本化操作”和 `声明：<工具>` 行。“脚本化操作”使用 presentation 范围的 `kind=code_mode_script_operation` facet，只匹配安全声明 request 索引中缺席的 Code Mode event。选择声明行会原子设置 `kind=code_mode_operation` 与 `codeModeRequest=<tool>`；选择“脚本化操作”或其他类型会清除该细分。生效筛选投影会把任一内部表示显示为一个类型标签和一次计数。Protocol 与 Raw 的 request 和“脚本化操作”目录为空，因此不显示该分组；既有层级切换仍会清除 `codeModeRequest`。不再存在筛选字段草稿、添加菜单或逐行移除动作。涉及文件组合框保持焦点时，候选表面会持续打开；当当前范围和层级没有文件，或输入片段过滤掉全部候选时，会显示与原因对应的空状态。候选层使用相对视口的浮层定位，与输入框对齐，并在下方空间不足时向上展开，因此可滚动的搜索辅助正文不会再裁切它。空闲状态会在表达式生效前隐藏计数、导航提示和“全部清除”。层级行会关闭弹层并聚焦相邻的顶部选择器，不会引入第二个选择器或状态。当前 session 的紧凑计数只显示“当前位置 / 已发现跳转目标”；全文 occurrence 及其可能增长的说明保留在生效结果表面中。项目紧凑计数显示匹配 session 数，结果表面与摘要显示匹配 session/event 总数，并且不出现上一个/下一个控件。普通 session 行、项目结果行、timeline 数据、候选和目标发现分别使用独立的请求 generation 与已提交 context key。项目表达式编辑会在 debounce 前启动明确的 pending 转换：使上一请求 generation 失效、清空卡片和聚合计数、隐藏结果摘要，并显示“搜索中”，直到 `projectSearchDataContextKey()` 提交。Session 范围的 query 编辑只刷新 timeline 查找状态；session 范围的结构化筛选编辑只重载所选 timeline；项目范围的表达式编辑只重载项目结果，绝不自动选择卡片。在当前 session 范围中，只要结构化事件筛选生效，任何自然 Folding Strategy 状态为 `hidden` 的返回事件都会被临时提升到 `collapsed`；该可见性下限不会修改 profile、canonical event、结果计数、分页或手动覆盖，清除筛选后即恢复自然折叠。项目结果下钻会捕获项目结果 context，显式切换到 session 范围，以不超过 500 条的 chunk 连续加载到 `latestEvent.timelineIndex + 1`，并在前缀提交前若范围、表达式、事件层、session 或 locale 变化就停止。

Command logical events build `searchText` from the command text plus canonicalized output parts. Output chunks are collected across all command lifecycle rows, including begin, update, delta, and end rows, so incremental output remains searchable even when the final row omits earlier chunks. When a parsed function-call output, aggregate output, or formatted output covers existing chunks, it replaces those covered chunks as the canonical body; candidates that contain different non-covered text are still retained once. Inferred touched files are also indexed so path searches remain discoverable. The logical event does not concatenate every mirrored command-output carrier, which keeps `searchMatchCount` from inflating when the same text appears in `stdout`, `aggregated_output`, `formatted_output`, raw row `searchText`, and `function_call_output`.

Command 逻辑事件会用命令文本加规范化后的输出片段来构造 `searchText`。输出 chunk 会从所有 command lifecycle row 收集，包括 begin、update、delta 和 end 行，因此即使最终行没有包含早先 chunk，增量输出仍可搜索。当解析后的 function-call output、aggregate output 或 formatted output 覆盖已有 chunk 时，它会替代这些已覆盖 chunk，作为规范化主体；包含不同未覆盖文本的候选输出仍会保留一次。推断出的 touched files 也会被索引，以保持路径搜索可发现。逻辑事件不会拼接每一个镜像 command-output 载体，因此当同一文本同时出现在 `stdout`、`aggregated_output`、`formatted_output`、原始行 `searchText` 和 `function_call_output` 中时，`searchMatchCount` 不会被放大。

Frontend highlight rendering remains DOM-oriented, but navigation membership does not. In current-session scope, committed timeline DTOs with `hasSearchHit` discover one canonical event anchor each; HTML rendering only supplies zero or more disposable bindings. The browser still highlights complete phrase matches in visible timeline events and the selected-event Inspector while excluding interactive, hidden, unsafe, Raw refs, profile-editor, control, summary, and chrome nodes. Multiple marks—including the same phrase projected in both timeline and Inspector—bind the same event anchor and cannot create or order members. Inspector-only supplemental text is highlight-only and has no canonical fallback because its owner is absent from the committed matching-event corpus. Project result snippets remain separate markup and never register anchors. Backend `searchMatchCount` remains the independent occurrence count for loaded and unloaded content. Navigation prefers a live timeline binding, may fall back to an Inspector binding of the same canonical event, and materializes event detail when neither is live; ordinary highlight refresh remains passive. / 前端高亮渲染仍面向 DOM，但导航成员关系不面向 DOM。在当前 session 范围内，已提交 timeline DTO 中每个 `hasSearchHit` 事件发现一个 canonical 事件锚点；HTML 渲染只提供零个或多个可丢弃 binding。浏览器仍会在可见 timeline event 与所选事件 Inspector 中高亮完整短语，同时排除交互、隐藏、不安全、Raw refs、profile 编辑器、控制、摘要与 chrome 节点。多个 mark（包括同一短语同时投影在 timeline 与 Inspector 中）绑定同一事件锚点，不能创建成员或决定顺序。仅 Inspector 补充文本只参与高亮，不存在 canonical fallback，因为其 owner 不在已提交匹配事件语料中。项目结果 snippet 继续使用独立 markup，绝不注册锚点。后端 `searchMatchCount` 仍是覆盖已加载与未加载内容的独立 occurrence 计数。导航优先使用实时 timeline binding，也可回退到同一 canonical 事件的 Inspector binding；两者都不存在时才物化事件详情；普通高亮刷新保持被动。

前端高亮渲染仍以 DOM 为单位，但导航成员关系不再由 DOM 决定。在当前 session 范围中，HTML 渲染完成后，浏览器只遍历可见 timeline event 和选中事件 Inspector；嵌套的交互、隐藏或不安全节点会跳过，并用 `textContent` 为完整短语命中插入 `<mark>`，而不是重写 HTML 字符串。Session row、项目结果卡、Raw refs、空详情态折叠编辑器、搜索控制、结果摘要和其它 UI chrome 都不参与 session 目标发现。项目结果卡为 snippet 使用独立高亮标记，绝不注册 descriptor。匹配仍限制在单个 DOM text node 内，不会跨 HTML 节点拼接文本。界面当前位置来自下文所述的稳定 descriptor 注册表；后端 `searchMatchCount` 继续作为独立全文上下文，用于提示尚未加载或尚未渲染的内容。导航会把 descriptor 重新解析成具体实时 mark，展开关闭的补充 `<details>` 祖先后再滚动；普通高亮刷新保持被动。

Search-driven detail synchronization carries frontend-only provenance. Explicit search navigation opens the inspector as `searchTransient`, while timeline clicks, Raw refs/Inspect toggles, selected-event previous/next navigation, and navigation-category changes open or promote the detail view as `userConfirmed`. Passive highlight refresh from search-box typing never replaces or downgrades an existing `userConfirmed` inspector or raw-ref view, even when the new query has rendered hits on other events. Search refresh convergence closes only `searchTransient` event details when `q` becomes empty, the refreshed timeline reports no search hits, or the selected event in the refreshed loaded timeline no longer has `hasSearchHit`. User-confirmed inspector and raw-ref views are re-rendered across free-text changes and continue to rely on the current selected-event lookup to close when structured filters or layer changes remove the selected event from the active result context.

搜索驱动的详情同步携带仅前端使用的来源标记。明确的搜索导航会把 inspector 打开为 `searchTransient`，而时间线点击、Raw refs/Inspect 切换、选中事件上一个/下一个导航，以及导航类别变更会把详情打开或提升为 `userConfirmed`。由搜索框输入触发的被动高亮刷新不会替换或降级已有的 `userConfirmed` inspector 或 raw-ref 视图，即使新查询在其它事件上有已渲染命中。搜索刷新收敛只会在 `q` 变为空、刷新后的时间线报告没有搜索命中，或刷新后的已加载时间线中所选事件不再带有 `hasSearchHit` 时关闭 `searchTransient` 事件详情。用户确认的 inspector 和 raw-ref 视图会在自由文本变化时重新渲染，并继续依赖当前选中事件查找，以便在结构化筛选或事件层变化把所选事件移出当前结果上下文时关闭。

#### Search navigation state boundary / 搜索导航状态边界

The previous browser implementation derived highlight rendering, navigation order, and the jump-target denominator from one mutable array of live DOM `<mark>` nodes. Inspector and timeline redraws therefore mutated the collection being navigated: one reproduction changed `1 / 18` to `2 / 17`, then changed `18 / 18` to `17 / 33` during materialization. That failure established the requirement that live marks are disposable bindings rather than navigation state. / 之前的浏览器实现让一个可变的实时 DOM `<mark>` 数组同时承担高亮渲染、导航顺序和跳转目标分母。Inspector 与 timeline 重绘因此会修改正在导航的集合：一次复现先让 `1 / 18` 变为 `2 / 17`，随后在物化时又让 `18 / 18` 变为 `17 / 33`。该故障确立了实时 mark 只能作为可丢弃绑定、不能作为导航状态的要求。

The implemented registry uses the event-anchor model. A descriptor exists only for current-session navigation and its identity is the JSON tuple `[completeSemanticSearchKey, logicalEventId]`; presentation surface and occurrence index are deliberately absent. The folding-profile context remains part of the semantic key, including deterministic normalized unsaved rules, so draft edits, cancellation, and same-ID saves establish explicit reset boundaries. Descriptors are sorted by logical timeline position with event ID as the deterministic tie-breaker. `activeTargetId` is looked up after every insertion, so discovery before the active target cannot silently activate another member. Each descriptor owns separate timeline and Inspector binding lists; refresh replaces those lists, re-highlights, and binds marks only to already-discovered event anchors. It never discovers from an Inspector render. Loading a later timeline page may append concrete new IDs; `Load more` stops at the first page sequence that yields one or more new IDs, does not synchronize detail, and marks exhaustion only after the timeline corpus is exhausted. A persisted manual fold remains authoritative, so a registered event anchor can be temporarily unresolvable without being removed or renumbered. / 已实现 registry 采用事件锚点模型。Descriptor 只存在于当前 session 导航中，其身份为 JSON tuple `[完整语义搜索 key, 逻辑事件 ID]`；展示 surface 与 occurrence index 被有意排除。折叠 profile context（包括确定性规范化的未保存规则）仍属于语义 key，因此草稿编辑、取消与同 ID 保存形成明确 reset 边界。Descriptor 按逻辑时间线位置排序，并以事件 ID 作为确定性并列规则。每次插入后都通过 `activeTargetId` 查找位置，因此在活动 target 前发现新成员不会静默激活另一成员。每个 descriptor 分别拥有 timeline 与 Inspector binding 列表；刷新会替换这些列表、重新高亮，并只把 mark 绑定到已发现的事件锚点，绝不从 Inspector 渲染发现成员。加载后续 timeline 页面可以追加具体新 ID；“加载更多”在一段页面首次产生一个或多个新 ID 时停止，不同步详情，并且只有时间线语料耗尽后才标记 exhaustion。持久化手动折叠保持权威，因此已注册事件锚点可以暂时无法解析，而不会被移除或重新编号。

Descriptor discovery is also gated by committed render context. Ordinary session-list requests carry repository, ordinary sort, and locale context; project-result requests carry repository, scope, active expression, layer, project-result sort, and locale; timeline requests carry selected session, scope, free text, structured filters, layer, folding-profile context, timeline sort, and locale. A response may update state only while both its generation and captured context still match. Timeline and detail renders stamp their surface context, and session-target discovery begins only when the current-session timeline surface is committed. As a second defense, a DOM owner must still exist in the committed `currentEvents` collection; Inspector discovery additionally requires the committed detail owner and current timeline membership. Navigation, target preloading, and visible-detail prefetch remain disabled while this barrier is pending, and zero-size hidden timeline surfaces are excluded from visibility checks. Project result cards have their own committed project-result context and are not considered target owners. / Descriptor 发现还受已提交渲染上下文的门控。普通 session 列表请求携带 repository、普通排序和 locale context；项目结果请求携带 repository、scope、生效表达式、事件层、项目结果排序和 locale；timeline 请求携带所选 session、scope、自由文本、结构化筛选、事件层、折叠 profile context、timeline 排序和 locale。只有 generation 与捕获 context 都仍匹配时，响应才能更新状态。Timeline 和 detail 渲染会记录各自的 surface context，只有当前 session timeline surface 已提交后才开始 session 目标发现。作为第二道防线，DOM owner 还必须存在于已提交的 `currentEvents` 集合中；Inspector 发现还要求已提交的 detail owner 和当前 timeline 成员关系。该屏障处于 pending 时，导航、目标预加载和可见详情预取保持禁用，并且尺寸为零的隐藏 timeline surface 不参与可见性判断。项目结果卡拥有自己的已提交项目结果 context，不会被视为目标 owner。

Navigation is a serialized asynchronous state transition. A FIFO queue lets one action own page loading, transient expansion, detail rendering, highlight refresh, descriptor resolution, supplemental `<details>` opening, and scrolling before the next action begins. Each action attempts any descriptor at most once, continues past temporarily unresolvable descriptors, includes descriptors appended by its own materialization, and only then wraps; this bounds failure handling without shrinking the denominator. Programmatic search scrolling cannot trigger timeline auto-pagination; explicit navigation decides when to load. The denominator may grow when a transition discovers new descriptors, but the active identity and its known position do not regress, and wrapping occurs only after the filtered timeline is exhausted. / 导航是串行异步状态转换。FIFO 队列让一次动作完整拥有分页加载、临时展开、详情渲染、高亮刷新、descriptor 解析、补充 `<details>` 展开和滚动，之后才开始下一次动作。每次动作对任一 descriptor 最多尝试一次，会越过暂时无法解析的 descriptor，并纳入本次物化追加的 descriptor，之后才允许回绕；这在不缩小分母的前提下为失败处理提供了上界。程序化搜索滚动不会触发 timeline 自动分页；是否加载由显式导航决定。转换发现新 descriptor 时分母可以增长，但活动身份及其已知位置不会倒退，且只有筛选后的 timeline 耗尽后才会回绕。

Search-assist visibility is an explicit interaction state. Focus and click are equivalent open intents, including clicks on an already-focused input; search-driven scrolling is guarded from dismissing the assist or triggering automatic pagination, while user scrolling outside the focused field can still dismiss it. Qualifying wheel, touch, pointer, or scrolling-key input in the timeline explicitly ends that programmatic guard; the subsequent actual downward timeline scroll event owns the next-page check, so a user takeover cannot lose the bottom-of-timeline transition or turn a non-scrolling input into pagination. The HUD remains one line at every supported width and always projects scope as the concise `session` / `project` labels, while the parameter popover retains the full scope names. When the search field has less than roughly 460 px, it hides only the compact metric text while retaining scope, filter count, input, and session navigation; the adjacent canonical Layer selector remains outside the HUD. At 760 px and below the popover becomes viewport-bounded and scrollable. Escape closes file suggestions before it closes the popover. / 搜索辅助面板可见性是显式交互状态。Focus 和 click 表达等价的打开意图，包括点击已经聚焦的输入框；搜索驱动滚动由 guard 阻止关闭辅助面板或触发自动分页，而焦点已离开输入框时的用户滚动仍可关闭它。时间线内合格的滚轮、触摸、指针或滚动键输入会明确结束程序化 guard；随后实际向下的时间线 scroll 事件拥有下一页检查，因此用户接管滚动时既不会遗漏时间线底部转换，也不会让未滚动的输入变成分页。HUD 在所有支持宽度下都保持单行，并始终以简洁的 `session` / `project` 标签投影范围，参数弹层则保留完整范围名称。当搜索区域不足约 460 px 时，只隐藏紧凑计数文本，仍保留范围、筛选数、输入和 session 导航；相邻的唯一层级选择器位于 HUD 之外并继续保留。在 760 px 及以下，弹层受视口约束且可滚动。退出键会先关闭文件候选，之后再关闭弹层。

`Read from here` bridges structured-filter and Layer views back to normal reading. When a selected event is shown while structured filters or a non-main Layer is active, the inspector and raw refs views expose a contextual action that clears the event filters, switches to `Main timeline`, and restores focus using the same timestamp/line anchor logic as Layer switches. If the exact selected event is not visible in Main timeline, the frontend selects the nearest visible event in timeline order. On narrow screens the action returns the user to the Events tab after the anchor is restored.

`Read from here` 用来把结构化筛选或事件层视图带回常规阅读。当选中事件处在结构化筛选或非主时间线事件层下时，检查器和原始引用视图会显示上下文动作；该动作会清除事件筛选、切换到 `Main timeline`，并复用事件层切换所用的 timestamp/line 锚点逻辑恢复焦点。如果精确的选中事件在 Main timeline 中不可见，前端会按时间线顺序选择最近的可见事件。在窄屏上，锚点恢复后该动作会把用户带回 Events 标签页。

The state and timeline payloads include `eventKinds` grouped by `main`, `protocol`, and `raw` layers. Main options retain disjoint logical `kind` values, including canonical `code_mode_operation` and `other_tool_call` rows with independent counts. The Code Mode kind's display label is `Code Mode tool call` / `Code Mode 工具调用`; a separate presentation-only `code_mode_script_operation` facet identifies operations without safe declared-request facts. Protocol options are logical `subtype` values, and raw options are `payloadType || recordType` values. The browser uses the selected session's timeline payload to populate the GUI `kind` filter picker and event counts in current-session scope, and the project-level state payload in project scope or before a session is selected. Backend values remain open-ended and retain subtype-compatible matching for unrelated existing cases, but Code Mode identity is matched by canonical kind. The browser hides the broad Code Mode kind row and exposes its Scripted-operation and declared-request children instead.

状态载荷和时间线载荷包含按 `main`、`protocol` 和 `raw` 层分组的 `eventKinds`。Main 选项保留互不重叠的逻辑 `kind` 值，其中规范 `code_mode_operation` 与 `other_tool_call` 各自拥有独立计数。Code Mode kind 的显示名为 `Code Mode tool call` / `Code Mode 工具调用`；另一个仅用于呈现的 `code_mode_script_operation` facet 标识缺少安全声明 request 事实的 operation。Protocol 选项使用逻辑 `subtype` 值，raw 选项使用 `payloadType || recordType` 值。浏览器在当前 session 范围使用选中 session 的时间线载荷填充 GUI `kind` 筛选选择器及 event 计数，在项目范围或尚未选中 session 前使用项目级状态载荷。后端值继续保持开放，并为其它既有情形保留 subtype 兼容匹配，但 Code Mode identity 通过规范 kind 匹配。浏览器隐藏宽泛的 Code Mode kind 行，改为暴露“脚本化操作”和声明 request 子项。

状态载荷和时间线载荷包含按 `main`、`protocol` 和 `raw` 分组的 `eventKinds`。Main 选项使用逻辑事件 `kind`，protocol 选项使用逻辑事件 `subtype`，raw 选项使用 `payloadType || recordType`。浏览器在当前 session 范围使用选中 session 的时间线载荷填充 GUI `kind` 筛选选择器及事件计数，在项目范围或尚未选中 session 前使用项目级状态载荷。后端中的值仍保持开放，并按事件 `kind` 或 `subtype` 匹配。

Search-result preloading is intentionally bounded. When free-text search has too few known descriptors, the browser may append a few timeline pages so previous/next navigation has nearby real targets. Explicit navigation is stronger than preload and can keep loading until the next hit owner is present or the filtered timeline is exhausted. Page rendering registers newly visible descriptors before scanning resumes, so the transition selects the first newly discovered semantic target instead of loading past it. A hit owner without a resolvable live mark may be temporarily expanded and loaded; that expansion stays keyed to the semantic search target and remains below persisted user overrides.

搜索结果预加载有意保持有限。当自由文本搜索下已知 descriptor 过少时，浏览器可以追加少量 timeline 分页，让上一个/下一个导航拥有附近的真实目标。显式导航强于预加载，可以继续加载，直到下一个命中 owner 出现或筛选后的 timeline 耗尽。分页渲染会先注册新可见 descriptor，再继续扫描，因此 transition 会选择第一个新发现的语义目标，而不会越过它继续加载。命中 owner 若没有可解析的实时 mark，可以被临时展开并加载；该展开继续绑定到语义搜索目标，且优先级低于持久用户覆盖。

### Timeline transition intent and request ownership / 时间线转换意图与请求 ownership

Timeline replacement and ordinary append now use separate authority. Every replacement starts a monotonic pagination epoch before the request or DOM replacement, clears any inherited user authorization, and remains pending until the new page and its viewport policy commit. Wheel, touch movement, pointer drag, and downward scrolling-key input can create one ordinary bottom-append candidate only after that epoch commits and while pagination is available and idle. The candidate is insufficient by itself: it must be followed by an observed positive timeline `scrollTop` delta in the same continuous sequence. Reverse or zero movement immediately cannot append; `Shift+Space` and wheel/key input with modifiers are not qualifying candidates. The candidate has a short no-scroll expiry. Once a real downward scroll is observed above the threshold, consecutive positive scroll events retain the same authorization through a short settle boundary so touch or trackpad inertia can reach the bottom; a reverse move or settling above the threshold revokes it. The scroll handler processes and revokes the token before loading, missing-session, or exhausted-timeline early returns, while the input handler refuses to issue a token during loading so delayed scroll delivery cannot reopen the race. Application-driven timeline `scrollIntoView` clears the user sequence before starting the programmatic-scroll guard. A qualifying token is consumed at the final `loadTimeline(true)` authorization point. If a current-context page-zero replacement fails, a dedicated retry state keeps ordinary append unavailable and turns the timeline action into a same-context offset-zero retry; only a successful replacement restores normal Load more behavior. Explicit Load more, search preload/navigation, selected-event loading, focus restoration, Layer restoration, project drill-down, and `Read from here` use typed programmatic intents instead of forging scroll state. Activating an interactive control or merely pressing the pane inside the timeline is not also counted as pointer or keyboard scrolling, so one explicit Load more action cannot leave a second ordinary append authorization. / 时间线替换与普通追加现在使用不同的授权。每次替换都会在请求或 DOM 替换前启动单调递增的分页 epoch、清除所有继承的用户授权，并保持 pending，直到新分页及其视口策略提交。只有该 epoch 提交且分页可用并处于 idle 时，滚轮、触摸移动、指针拖动与向下滚动键输入才能创建一次普通底部追加候选。候选本身不足以分页：它还必须由同一连续序列中观察到的时间线 `scrollTop` 正向 delta 支持。反向或零移动不能追加；`Shift+Space` 以及带修饰键的滚轮/按键都不是合格候选。候选具有短暂的无滚动失效时限。观察到停在阈值上方的真实向下滚动后，连续正向 scroll 事件会在短暂 settle 边界内保留同一授权，使触摸或触控板惯性可以继续触底；反向移动或最终停在阈值上方都会撤销它。Scroll handler 会在 loading、缺少 session 或时间线耗尽等 early return 之前先处理并撤销 token；input handler 也会拒绝在 loading 期间签发 token，避免延迟交付的 scroll 重新打开竞态窗口。应用驱动的时间线 `scrollIntoView` 会在启动程序化滚动 guard 前清除用户序列。合格 token 会在最终 `loadTimeline(true)` 授权点消费。如果当前 context 的第零页替换失败，专用 retry 状态会让普通追加保持不可用，并把时间线操作变为同 context 的 offset-zero 重试；只有替换成功才恢复普通“加载更多”行为。显式“加载更多”、搜索预加载/导航、所选事件加载、焦点恢复、事件层恢复、项目下钻与“从此处阅读”使用 typed programmatic intent，而不是伪造 scroll 状态。激活交互控件或只在时间线面板内按下指针，不会同时被计为 pointer 或 keyboard 滚动，因此一次显式“加载更多”不能遗留第二次普通追加授权。

A structured-filter or Clear-all replacement captures the selected event before requesting page zero. After the current request generation and complete timeline context commit, the selection is restored only when that exact event is in the committed first page; otherwise the selection closes and the pane resets to top. Layer switches and `Read from here` retain their explicit full-result anchor lookup and contiguous-prefix loading, while the replacement epoch prevents residual scroll from joining that deliberate sequence. Query-only refresh continues to refetch the previously materialized depth and preserve scroll. / 结构化筛选或“全部清除”替换会在请求第零页前捕获已选事件。当前请求 generation 与完整 timeline context 提交后，只有该精确事件位于已提交第一页时才恢复选择；否则关闭选择并把面板重置到顶部。事件层切换与“从此处阅读”继续保留显式的完整结果锚点查找和连续前缀加载，同时 replacement epoch 会阻止残留 scroll 加入这段有意序列。只修改 query 时继续重取之前已物化的深度并保留滚动。

Transition-sensitive browser requests keep both cancellation ownership and stale-commit guards. Selected timeline operations, ordinary Session lists, project results, analysis, file suggestions, Inspector navigation scans, and event-envelope reads each have an independent single-current owner. Event detail uses a controller map keyed by `(sessionId, layer, eventId, detailCacheGeneration)` so unrelated visible details remain independent; cache-generation reset aborts the map. Raw References use one controller for the current selection's group of `/api/raw` reads. A selected detail also captures a committed render context of repository, scope, Session, Layer, structured filters, locale, and detail-cache generation. Scope-to-project, Layer, Session, repository, close/back, and `Read from here` transitions invalidate that selection and abort only its matching detail-map controller plus its Raw Reference owner; unrelated per-event detail loads remain independent. Starting a superseding request aborts only its owner's prior controller; success, error, abort, and `finally` mutations still require current owner identity plus the existing generation/context checks. Intentional abort is recognized as a typed `DOMException` with name `AbortError`, never by message text, and never enters `showError` or commits a zero-result/cache/error state. Browser fetch cancellation propagates through the HTTP disconnect to the source-neutral adapter signal, so abandoned active Codex scans stop and queued scans can be discarded before I/O. The stable `INDEXED_SOURCE_STALE` response code is preserved separately from localized display text; detail and Raw-reference surfaces route it to the existing project-reindex workflow, ordinary detail errors keep the existing Retry behavior, and other Raw-reference failures keep their existing handling. / 转换敏感的浏览器请求同时保留取消 ownership 与过期提交 guard。所选时间线操作、普通会话列表、项目结果、分析、文件候选、检查器导航扫描与 event envelope 读取分别拥有彼此独立的单一 current owner。事件详情使用以 `(sessionId, layer, eventId, detailCacheGeneration)` 为 key 的 controller map，使无关的可见详情彼此独立；cache generation 重置时会取消整张 map。原始引用为当前选择的一组 `/api/raw` 读取使用一个 controller。已选详情还会捕获由仓库、范围、session、事件层、结构化筛选、locale 与 detail-cache generation 组成的已提交渲染 context。切到项目范围、事件层、session、仓库、关闭/返回以及“从此处阅读”转换会使该选择失效，并且只取消匹配的 detail-map controller 与其原始引用 owner；无关的逐事件详情加载继续独立。启动取代请求时只取消该 owner 的旧 controller；success、error、abort 与 `finally` mutation 仍同时要求 current owner identity 和既有 generation/context check。Intentional abort 只识别 name 为 `AbortError` 的 typed `DOMException`，绝不依赖 message 文本，也绝不进入 `showError` 或提交零结果、cache 或错误状态。浏览器 fetch 取消会通过 HTTP disconnect 传播到来源中立的 adapter signal，因此已放弃的活跃 Codex 扫描会停止，排队扫描也能在 I/O 前丢弃。稳定的 `INDEXED_SOURCE_STALE` 响应 code 会与本地化显示文本分开保留；detail 与原始引用界面会把它导向既有项目重新索引流程，普通 detail 错误保留既有重试行为，其它原始引用错误保留既有处理方式。

The shared browser API retries one GET exactly once when the runtime responds with `503 MATERIALIZATION_BUSY`, using a bounded `Retry-After` delay and the request's existing abort signal. A second busy response follows the normal surface-specific error and explicit Retry behavior; non-GET mutations and all other HTTP failures are never replayed by this rule. / 当 runtime 返回 `503 MATERIALIZATION_BUSY` 时，共享 browser API 会使用有界 `Retry-After` 延迟与该请求既有 abort signal，对 GET 精确重试一次。第二次 busy 响应进入普通的界面专属错误与显式重试行为；非 GET mutation 及所有其它 HTTP failure 绝不会由此规则重放。

展开卡片不会复用 `preview` 进行富渲染。服务器会根据底层逻辑事件及其引用的原始行派生 `EventDetailDto`：

`meta` 始终包含 `timestamp`、`turnId`、`status`、`severity`、`toolName`、`touchedFiles`、`outputStats`、`channels` 和 `source`。

The same fact is included in the event search text, while Raw References remain the authority for the source row. / Claude 的来源支撑 provenance 是增量字段：当一个 Logical Event 具有唯一的规范化 `attributionSkill` 时，detail `meta` 可以暴露 `provenance: { attributionSkill }`；畸形或冲突值会被省略。同一事实也会进入 event search text，而 Raw Reference 仍是来源记录的权威。

#### Accepted two-axis Structured Detail architecture / 已接受的二维结构化详情架构

Structured Detail has two orthogonal semantic axes. Every section in a Main- or Protocol-layer Event Detail carries one `purpose` from the closed source-neutral vocabulary, which states what the information means. Its containing array carries Detail Responsibility, which states the section's role in reading the event. `type` remains the closed renderer discriminant that states how the payload is drawn. Localized `title`, source-owned title text, `hideTitle`, renderer type, and producer order establish neither purpose nor responsibility. / 结构化详情具有两条正交语义轴。Main 或 Protocol 层 Event Detail 的每个 section 都从封闭的来源中立词汇中携带一个 `purpose`，说明信息是什么；承载它的数组表达详情职责，说明该 section 在阅读事件时承担什么作用。`type` 继续作为封闭 renderer 判别字段，说明 payload 如何绘制。本地化 `title`、来源拥有的标题文本、`hideTitle`、renderer type 与 producer 顺序既不建立 purpose，也不建立 responsibility。

| `purpose` | Normative meaning / 规范含义 | Examples, not definitions / 示例而非定义 |
| --- | --- | --- |
| `content` | A coherent event-specific body meant to be read as one unit and not usefully separated into request/result stages. / 应作为一个整体阅读、且不适合拆成 request/result 阶段的事件专属正文。 | message, reasoning, plan body, user-input interaction, collaboration card / 消息、推理、计划正文、用户输入交互、协作卡片 |
| `request` | What an operation was asked or declared to do, without claiming execution or success. / 某次操作被请求或声明要做什么，不声称已经执行或成功。 | command, patch input, tool arguments, declared Code Mode request / 命令、patch 输入、工具参数、已声明 Code Mode request |
| `result` | An observed output, response, completion, or outcome owned by the selected event. / 所选事件拥有的已观测输出、响应、完成事实或结果。 | stdout/stderr, tool response, applied diff, lifecycle completion / stdout/stderr、工具响应、已应用 diff、生命周期完成事实 |
| `context` | Event-specific supporting facts needed to interpret content, request, or result, excluding common envelope metadata. / 理解 content、request 或 result 所需的事件专属辅助事实，不包括通用 envelope metadata。 | run context, usage, files, launch state, source-owned options / 运行上下文、用量、文件、启动状态、来源专属选项 |
| `traceability` | How the analyzer related or projected evidence, or a relation to another canonical event; it explains interpretation but is not source evidence itself. / Analyzer 如何关联或投影证据，或与另一 canonical event 的关系；它解释解释过程，但不是来源证据本身。 | projection evidence, execution trace, observed nested event links / 投影证据、执行 trace、已观测嵌套事件链接 |
| `fallback` | Bounded, sanitized material whose semantic role cannot safely be identified as `content`, `request`, `result`, `context`, or `traceability`. / 无法安全识别为 `content`、`request`、`result`、`context` 或 `traceability` 的有界、已脱敏材料。 | unclassified logical fragment, bounded logical Raw JSON for an already admitted event / 未分类 logical fragment、已接纳事件的有界 logical Raw JSON |

Detail Responsibility has two values encoded by the existing containers, not by a duplicate section field: / 详情职责有两个值，由既有容器编码，不在 section 上增加重复字段：

| Container / 容器 | Normative responsibility / 规范职责 | Meaning / 含义 |
| --- | --- | --- |
| `timelineSections[]` | Primary Detail / 主体详情 | The event-specific readable representation needed to understand what happened while following chronological work history. It makes the event intelligible without opening the Inspector. / 沿时间顺序阅读工作历史时，为理解发生了什么所必需的事件专属可读表示；无需打开 Inspector 即可理解该事件。 |
| `inspectorSections[]` | Supplemental Detail / 补充详情 | Additional structured information useful for inspection, verification, provenance, debugging, or deeper understanding, but not required to follow chronological work history. / 对检查、核验、来源追溯、调试或深入理解有用，但并非沿时间顺序理解工作历史所必需的附加结构化信息。 |

Purpose does not map mechanically to responsibility. An assistant message body, plan body, command request, observed stdout／stderr, or applied patch can be Primary Detail. Full tool arguments, a second structured output projection, cwd／run options, touched-file inventory, projection evidence, and bounded fallback fields are normally Supplemental Detail. `content`, `request`, and `result` may occur in either container when the definitions justify it; `context` is rarely primary; `traceability` and `fallback` are supplemental unless a future reviewed contract gives a concrete source-neutral counterexample. These examples guide semantic judgment but are not title, kind, or renderer lookup tables. / Purpose 不机械映射到 responsibility。Assistant message 正文、plan 正文、command request、已观测 stdout／stderr 或已应用 patch 可以属于主体详情。完整工具参数、第二份结构化输出投影、cwd／运行选项、触达文件清单、投影证据与有界 fallback field 通常属于补充详情。当定义成立时，`content`、`request` 与 `result` 可以出现在任一容器；`context` 很少属于主体；`traceability` 与 `fallback` 属于补充，除非未来经过评审的契约给出具体且来源中立的反例。这些示例用于指导语义判断，不是 title、kind 或 renderer lookup table。

A section has exactly one purpose. A top-level or nested composite that must remain atomic uses outer `content`; that outer purpose alone controls its global Inspector placement. Nested child sections still require purposes for renderer-local meaning and order, but the shared Inspector never hoists, splits, or reorders those children across top-level purpose groups. Scalar evidence badges embedded by the renderer remain display fields of the atomic content; a standalone projection-evidence section uses `traceability`. This avoids a generic `mixed` purpose while preserving established composite presentation where the combination is itself meaningful. / 一个 section 只能有一个 purpose。必须保持原子性的顶层或嵌套 composite 使用外层 `content`；只有该外层 purpose 控制其在 Inspector 中的全局位置。嵌套子 section 仍必须携带 purpose，供 renderer 局部表达含义和排序，但共享 Inspector 绝不会把这些子 section 提升、拆分或跨顶层 purpose 分组重排。Renderer 内嵌的标量 evidence badge 继续作为原子 content 的显示字段；独立的投影证据 section 使用 `traceability`。该规则既避免引入泛化的 `mixed` purpose，也能在组合本身有意义时保留既有复合呈现。

The same renderer can serve different purposes. A `patch` may be a requested change or an observed applied diff; a `notice` may be content, result, context, traceability, or fallback. Conversely, one purpose may use several renderer types. Therefore neither renderer type nor title is a semantic alias. Rendering genericness and modeling specificity are not purpose axes: a generic JSON or code summary that the adapter knows is a request or result must use `request` or `result`, never `fallback`. Producer order is only a within-purpose narrative tie-breaker. / 同一个 renderer 可以服务不同 purpose。`patch` 可能是请求的改动，也可能是已观测的 applied diff；`notice` 可能属于 content、result、context、traceability 或 fallback。反过来，一个 purpose 也可以使用多种 renderer type。因此 renderer type 与 title 都不是语义 alias。渲染是否通用、建模是否具体都不是 purpose 轴：adapter 已知属于 request 或 result 的通用 JSON／code 摘要必须使用 `request` 或 `result`，绝不能使用 `fallback`。Producer 顺序只作为同一 purpose 内的叙事顺序 tie-breaker。

Detail Purpose and Detail Responsibility are response-time presentation semantics, not canonical facts. Neither is added to Index, Session, Logical Event, Raw Record, search, metrics, folding, status, or Raw-reference ownership. The owning adapter assigns both while interpreting selected-event source evidence. The shared detail boundary validates purpose, responsibility-container invariants, and renderer shape without reclassification. The browser renders Primary Detail in the expanded timeline body and Supplemental Detail in the Inspector without moving sections between containers. / 详情用途与详情职责都是响应期呈现语义，而不是 canonical fact。两者都不会加入 Index、Session、Logical Event、Raw Record、搜索、指标、折叠、status 或 Raw-reference ownership。所属 adapter 在解释选中事件的来源证据时同时分配二者。共享详情边界校验 purpose、responsibility-container invariant 与 renderer shape，不重新分类。浏览器在展开 timeline 正文渲染主体详情，在 Inspector 渲染补充详情，不在容器之间移动 section。

The normative two-axis requirement covers structured logical detail in `main` and `protocol`. Raw-layer detail remains a separate source-evidence presentation. The current container names are retained for wire compatibility, but their meanings are now normative: `timelineSections[]` is Primary Detail and `inspectorSections[]` is Supplemental Detail. Equivalent responsibility cannot change because an adapter selected a different renderer type, localized title, source kind, or producer order. / 规范二维要求覆盖 `main` 与 `protocol` 中的结构化 logical detail。Raw 层详情继续作为独立来源证据呈现。当前容器名为 wire compatibility 保留，但其含义现在是规范性的：`timelineSections[]` 是主体详情，`inspectorSections[]` 是补充详情。Adapter 选择不同 renderer type、本地化 title、source kind 或 producer 顺序时，等价责任不得变化。

The source-neutral conformance matrix tests that responsibility rule over stable cross-source archetypes rather than introducing runtime `kind → responsibility` inference. Controlled Codex and Claude Code fixtures cover user and assistant messages, commands, file changes, MCP operations, web operations, and plan updates. The matrix checks only shared responsibility invariants; fixture-unique evidence additionally proves that complete command and MCP request objects remain Supplemental even when their concise request or readable result is Primary. Renderer type, title, section count, and producer order are not archetype selectors. / 来源中立 conformance matrix 会在稳定的跨来源 archetype 上测试该职责规则，而不会引入 runtime `kind → responsibility` 推断。受控的 Codex 与 Claude Code fixture 覆盖用户消息、助手消息、命令、文件改动、MCP 操作、Web 操作与计划更新。矩阵只检查共享职责不变量；fixture 唯一证据还会证明，即使简明 request 或可读 result 属于主体，完整 command／MCP request object 仍属于补充详情。Renderer type、title、section 数量与 producer 顺序都不是 archetype selector。

After M3, shared consumption follows one fixed sequence: (1) resolve exact canonical Index → Session → Logical Event ownership and every referenced Raw Record; (2) let the owning adapter hydrate structured detail; (3) require exact equality between the response and the selected canonical event／request envelope for immutable `id`, `schemaVersion`, `sourceKind`, `kind`, `subtype`, `layer`, `sourceLocator`, and ordered deep `rawRefs`; (4) validate bounded recursion, plain containers, closed purpose／renderer discriminants, and type-specific shapes, then apply type-aware sanitization; and (5) validate the final emitted shape. Complete `rawRefs` cannot be omitted, added, reordered, or rewritten. Missing or unknown purposes/types and malformed shapes fail with an explicit contract error; they are never coerced from title, source kind, tool name, or array position. / M3 完成后，共享消费遵循固定顺序：（1）解析精确的 canonical Index → Session → Logical Event ownership 及其引用的每条 Raw Record；（2）由所属 adapter hydrate 结构化详情；（3）要求响应与所选 canonical event／请求 envelope 的不可变字段精确相等，包括 `id`、`schemaVersion`、`sourceKind`、`kind`、`subtype`、`layer`、`sourceLocator` 与有序、深度相等的 `rawRefs`；（4）校验有界递归、plain container、封闭 purpose／renderer discriminant 与按 type 的 shape，再执行 type-aware 脱敏；（5）校验最终输出 shape。完整 `rawRefs` 不得被遗漏、增加、重排或重写。缺失或未知 purpose/type 及畸形 shape 会以明确契约错误失败；绝不会根据 title、source kind、tool name 或数组位置进行强制推断。

The type-aware sanitizer may redact or truncate leaf strings and omit optional excess only in schema-defined ways, including schema-defined omission markers. It never changes a purpose, renderer type, required container kind, immutable envelope field, Raw Reference, or source locator. Accessors, cycles, unknown discriminants, and over-budget containers fail before sanitization; sanitization does not repair a malformed DTO. Bounded material uses `fallback` only when its semantic role cannot safely be identified; generic but known requests and results retain `request` and `result`. Unknown or unsupported event shapes continue through Protocol and/or Raw rather than being promoted. / Type-aware sanitizer 只能脱敏或截断叶子字符串，并且只能按 schema 定义的方式省略可选超量内容，包括 schema 定义的 omission marker。它绝不会改变 purpose、renderer type、必需 container kind、不可变 envelope 字段、Raw Reference 或 source locator。Accessor、cycle、未知 discriminant 与超预算 container 必须在脱敏前失败；脱敏不能修复畸形 DTO。只有无法安全识别语义角色的有界材料才使用 `fallback`；通用但已知的 request 与 result 仍分别使用 `request` 和 `result`。未知或不受支持的 event shape 继续进入 Protocol 和／或 Raw，不得被提升。

## Detail panel and folding profiles / 详情面板与折叠策略

## Alternatives considered / 已考虑的备选方案

### Render raw transcript rows directly / 直接渲染原始转录行

- Pros: simplest parser, minimal inference / 优点：解析器最简单，推断最少
- Cons: duplicates everywhere, protocol noise dominates, poor default reading experience / 缺点：到处重复，协议噪声占主导，默认阅读体验差
- Rejected because it breaks the product goal of readable repository history / 已拒绝，因为它破坏了让仓库历史可读的产品目标

### Hide duplicated channels without adding event layers / 不新增事件层，只隐藏重复通道

- Pros: smaller implementation change / 优点：实现改动更小
- Cons: protocol rows and proposed plans still lack a stable place to live / 缺点：协议行和 proposed plan 仍然缺少稳定归属
- Rejected because it treats symptoms but not transcript structure / 已拒绝，因为它处理的是症状，而不是转录结构

### Persist a canonical normalized store / 持久化规范化的归一化存储

- Pros: faster reloads, easier offline analysis later / 优点：重新加载更快，之后更容易离线分析
- Cons: storage versioning and migration complexity / 缺点：存储版本和迁移复杂度
- Deferred because current product still prefers in-memory local processing / 已推迟，因为当前产品仍偏好内存中的本地处理

## Risks and failure modes / 风险和失效模式

- Over-aggressive deduplication may hide genuinely distinct rows / 过度激进的去重可能隐藏真正不同的行
- Historical tool formats may not provide enough metadata for perfect normalization / 历史工具格式可能无法提供足够元数据来实现完美归一化
- Protocol classification may need refinement as Codex transcript shapes evolve / 随着 Codex 转录形态演进，协议分类可能需要细化
- Search behavior may confuse users if matches only exist in protocol or raw layers / 如果匹配只存在于协议层或原始层，搜索行为可能让用户困惑

## Security / privacy / compliance / 安全 / 隐私 / 合规

- All transcript data stays local / 所有转录数据都保留在本地
- No transcript mutation / 不变更转录
- Raw transcript access remains explicit and traceable / 原始转录访问保持显式且可追踪
- Derived logical events should not expose more than the source rows already contain / 派生逻辑事件不应暴露超过来源行已经包含的内容
- For embedded data URLs, high-confidence encoded tokens may continue across whitespace boundaries, including wrapped base64 chunks and explicit `%HH`, uppercase, or symbol/numeric-only non-base64 tokens; ordinary prose starts a new searchable logical segment even when its words fit the base64 alphabet or contain path, snake_case, URL, `+`, or `=` punctuation / 对内嵌 data URL，高置信 encoded token 可以跨空白边界继续脱敏，其中包括换行包装的 base64 片段，以及明确的 `%HH`、全大写或仅符号／数字的非 base64 token；普通正文即使单词符合 base64 字母表，或包含路径、snake_case、URL、`+`、`=` 标点，也会开始新的可搜索逻辑片段
